## Задание

Собрать управляемый промпт, получить стабильный ответ модели и превратить его в небольшой полезный артефакт:

1. Выбрать бытовую мини-задачу.
2. Собрать промпт по схеме «роль → контекст → задача → формат ответа». Формат вывода — валидный JSON `{"title", "steps", "notes"}`.
3. Запустить в одном инструменте, зафиксировать модель, temperature (рекомендуют 0.2) и системные инструкции.
4. Сделать одну итерацию качества: уточнить роль **или** добавить few-shot пример. Повторить запуск с теми же параметрами.
5. Сравнить два ответа: соответствие JSON, полезность `steps`, лаконичность `notes` (до 3 тезисов).
6. Собрать артефакт: `README.md` или мини-скрипт.

## Что сделано

Задача — напоминание о приёме таблеток: пользователь пишет расписание своими словами, модель оформляет план напоминаний на день. Тестовый ввод: «Витамин D — 1 таблетка в 09:00 после еды; Магний — 1 таблетка в 21:00 перед сном». Препараты взяты безобидные и выдуманные для примера, реальные назначения в публичный репозиторий не попали.

| Требование | Где |
|---|---|
| Бытовая мини-задача | Напоминания о приёме таблеток по заданному времени |
| Промпт «роль → контекст → задача → формат» | [`prompts/v1.json`](prompts/v1.json): роль и контекст в `system`, задача и формат в `user` |
| Формат — валидный JSON | Три ключа `title`, `steps`, `notes`; шаги в виде «ЧЧ:ММ — препарат, доза, условие» |
| Инструмент, модель, параметры | Раздел «Условия запуска» ниже |
| Итерация качества | [`prompts/v2.json`](prompts/v2.json): уточнённая роль + few-shot пример |
| Сравнение двух ответов | Раздел «Прогоны», по три запуска на версию, сырые ответы в [`results/`](results/) |
| Артефакт | [`remind.py`](remind.py): запрос к модели, проверка JSON, вывод расписания; режим `--check` проверяет готовый ответ без ключа |

### Схема промпта

| Часть | Содержание |
|---|---|
| Роль | Помощник по организации напоминаний о приёме лекарств |
| Контекст | Не врач: не назначает препараты, не меняет дозировки и время, не даёт медицинских советов |
| Задача | Составить план напоминаний на день из расписания пользователя |
| Формат | Только JSON без пояснений и Markdown |

Ограничение «не врач» — самое важное в этом промпте: модель должна оформлять то, что дал пользователь, а не решать за него, когда и сколько принимать.

## Чем отличается от урока — и почему

В уроке всё запускалось через OpenAI API с ключом. Я работаю в Claude Code, поэтому запуск устроен иначе. По тексту урока заметила несколько мест, которые не повторила.

1. **Запуск без API.** Вместо `openai_direct.py` — прогоны в чистых контекстах и скрипт `remind.py`, который при наличии ключа повторяет то же самое через API.
2. **temperature не выставить.** В уроке её меняют в скрипте. У меня такого рычага нет, поэтому я не сравниваю 0.2 и 0.7, а сравниваю две версии промпта при одинаковых условиях и повторяю каждую трижды.
3. **Ошибки урока, которые не повторила:**
   - в итогах урока сказано «системные (Assistant) и пользовательские (User) промпты», но `system` и `assistant` — разные роли: `system` задаёт поведение, `assistant` — это ответы модели в истории, в том числе образец для few-shot. В `v2.json` обе роли использованы по назначению;
   - скрипт урока принимает temperature только от 0.0 до 1.0, хотя у API диапазон шире. В `remind.py` значение не ограничено искусственно;
   - у новых моделей лимит длины ответа может называться `max_completion_tokens`, а не `max_tokens`. Лимит в `remind.py` не задан вовсе, длину держит формат («до 3 тезисов»);
   - вывод урока «грамотный промпт даёт стабильный результат независимо от temperature» подтверждён на одной паре запусков. Я не принимаю это на веру: у меня три прогона на версию, и по ним видно, что стабильность зависит ещё и от примера (см. выводы).
4. **JSON вместо Markdown.** Урок показывает ответы в Markdown для человека. Здесь результат должна читать программа, поэтому ответ проверяется `json.loads` и схемой в `remind.py`.

## Выводы

1. **Формат JSON держат обе версии.** На такой простой задаче модель выдаёт валидный JSON и без примера: 6 из 6. Разница видна не в валидности, а в повторяемости.
2. **Few-shot даёт стабильность.** Три ответа v2 совпали полностью, три ответа v1 — нет (разные заголовки и `notes`). Для программы, которая показывает результат пользователю, одинаковый ответ на одинаковый ввод — важное свойство.
3. **Цена стабильности — копирование примера.** `notes` в v2 взяты из образца, а не выведены из ввода. Тезис «принимайте строго в указанное вами время» пользователь не писал. Здесь это безопасно: текст заранее проверен и ничего не советует по лечению. Но пример задаёт не только форму, но и содержание — в другой задаче так можно получить чужой текст.
4. **Роль защищает от лишних советов.** В v1 в одном прогоне из трёх появился совет о времени напоминания (P3). Это мелочь, но в медицинской теме именно такие отходы от роли нежелательны. В v2 этого не было.
5. **Итерация состоит из двух правок.** Я сделала уточнение роли и добавила пример сразу. Какая из них дала стабильность, по этим данным сказать нельзя: нужен отдельный прогон «v1 + только пример».
6. **Выборка маленькая:** три прогона, один ввод, одна модель, параметры по умолчанию. Это иллюстрация подхода, а не статистика.

## Что поправила по итогам

- В `remind.py` добавлена собственная проверка схемы: ключи, формат шага «ЧЧ:ММ — …», не более трёх `notes`. Одного `json.loads` мало: валидный JSON с неправильными ключами проходил бы.
- Из README убрано название модели: в отчёте указано, что модель не выбиралась, и это честнее, чем придуманная строка.

## Что не сделано

- `remind.py` не запускался с реальным API (нет ключа). Нужно проверить у себя: `python remind.py --version v2 --schedule "..."`.
- Не измерено влияние temperature, не проверены другие модели и другие расписания (три и больше препаратов, одно время на два препарата, пустой ввод).
